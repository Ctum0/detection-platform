# Security Policy

## Scope & Operational Context

`detection-platform` is an **experimental detection engineering platform, reference architecture, and research prototype**. It demonstrates end-to-end detection-as-code lifecycles, automated multi-backend Sigma compilation, purple-team adversary emulation validation, and analyst-augmented SOAR triaging.

This codebase is designed and intended for deployment and operation within **controlled lab environments, cyber ranges, and detection engineering testbeds**.

## Operational Safety & Attack Emulation Warnings

> [!WARNING]
> **Adversary Emulation Safety**: Attack scripts and automated test runners located in `attack-tests/` execute real-world adversary techniques (including process memory dumping emulation, registry persistence modifications, service creation, and PowerShell cradle execution).
> 
> **Never execute attack simulations or automated test runners against production systems, multi-tenant infrastructure, or networks you do not own and explicitly control.** All emulation must be confined to isolated virtual machines and segmented sandboxes.

## Production Hardening Considerations

For security teams adapting concepts from this project into enterprise production environments, the following architectural controls should be implemented:

1. **Identity & Access Management (IAM)**:
   - Replace pre-shared bearer tokens with enterprise Single Sign-On (SAML 2.0 / OIDC) and hardware-backed Multi-Factor Authentication (FIDO2 / WebAuthn).
   - Enforce granular Role-Based Access Control (RBAC) separating detection authors, reviewers, and pipeline administrators.
2. **Network Perimeter & Segmentation**:
   - Restrict access to the Operator Console, Wazuh Manager API (port 55000), and SOAR webhooks via an Identity-Aware Proxy (IAP), corporate VPN, or zero-trust overlay network (e.g. Tailscale).
   - Segregate victim VMs, attacker VMs, and management infrastructure into isolated VLANs with strict firewall boundaries.
3. **Secrets Management**:
   - Manage GitHub fine-grained Personal Access Tokens (PATs), webhook signing keys, and SIEM credentials through enterprise secret vaults (e.g. HashiCorp Vault, AWS Secrets Manager, CyberArk) rather than static environment variables.
   - Restrict GitHub PAT permissions strictly to specific detection repositories with least privilege.
4. **Detection Rule Safety & ReDoS**:
   - Custom user-authored Sigma rules should undergo static analysis and regular expression complexity checks to avoid Regular Expression Denial of Service (ReDoS) against high-throughput SIEM ingestion engines.
5. **Human-in-the-Loop Verification**:
   - Automated detection drafts generated by AI agents must always require human review and green CI validation before merging into production deployment branches.

## Reporting a Vulnerability

We take the security of this project seriously and appreciate responsible disclosure from the security research community.

If you believe you have found a security vulnerability or sensitive data exposure:

1. **Do NOT open a public GitHub issue or pull request.**
2. Send a private report to the maintainer at **sithumsryt@gmail.com**, or submit a confidential report via **GitHub Private Vulnerability Reporting** on the repository.
3. Please include:
   - A description of the issue and potential impact.
   - Step-by-step reproduction instructions or a minimal Proof of Concept (PoC).
   - Affected files, endpoints, or workflows.
   - Any proposed remediation or mitigation.

### Response & Disclosure Process

- **Acknowledgment**: You will receive an acknowledgment within 48 hours of receipt.
- **Assessment**: We will evaluate the report, verify the issue in our lab environment, and determine its severity and blast radius.
- **Remediation**: Once verified, a fix will be developed and committed.
- **Coordinated Disclosure**: We request that you maintain confidentiality until a fix has been published.
